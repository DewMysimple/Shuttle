# ADR-008｜完整帧时间切片

## 状态

`active`

## 背景

原网页只使用从 1–166 帧均匀抽取的 76 张 PNG。抽样能降低首屏资源量，但相邻动作状态之间会出现跳跃，且空间时间隧道中相邻切片的密度过高。用户要求保留源动画的全部帧，并增加相邻切片的物理间距。

## 决策

- 以 Blender 场景的整数帧范围为准，当前从第 1 帧到第 166 帧逐帧渲染，共 166 张 RGBA PNG。
- `slice-manifest.json` 是网页的帧数来源；前端先读取 manifest，再按 `count` 加载同编号 PNG，不再在源码中写死 76。
- 保留每张 PNG 的独立时间身份，长按播放将 `frameFloat` 推进到 `0–165`，并以 `index - frameFloat` 锚定当前帧。
- 将时间隧道空间步进调整为 X `0.16`、Z `0.30`；卡片和图片尺寸保持不变，展开按钮仍独立控制 `spread`。
- 继续只使用透明时间切片作为网页主体，不恢复实时 GLB 模型；`flower.glb` 仅用于导出检查。

## 理由

- 全整数帧避免 76 状态采样造成的时间跳跃，使滚动逐帧穿越更连续。
- 增加步进后，相邻切片保留更明确的轮廓和遮挡关系，侧面能看到独立序列，正面仍能通过透视形成时间隧道。
- manifest 驱动让后续更换帧范围时只需重新导出资产，不必再次修改前端常量。

## 影响

- 运行资产从 76 张 PNG 增加到 166 张，首屏请求数、传输体积和 GPU 纹理占用都会增加；移动端仍需要真实设备复核。
- 重新导出必须提供外部 `OrchidMeshGrp.abc`，且需核对 manifest 数量、PNG 编号连续性与透明边缘。
- 远端切片数量增加后，整体时间轨迹更长；视野内仍由焦点透明度和透视筛选可见层级。

## 验证方式

- Blender 导出日志显示 `frame-001.png` 至 `frame-166.png` 均成功保存。
- manifest `count` 为 166，`frames[].sourceFrame` 连续覆盖 1–166。
- `npm run build`、资源 HTTP 200、`git diff --check` 和 memory lint 均通过。
- 正面检查当前帧清晰度与隧道层级，侧面检查相邻切片间距；移动端检查加载与帧率。
